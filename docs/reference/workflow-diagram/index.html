상세페이지 생성 하네스 — 파이프라인 워크플로우

규제 대상 제품(화장품·의약외품·건기식·의약품)의 상세페이지/홍보물을 파일 기반 단계 게이트로 생성하는 파이프라인. 각 생성 페이즈는 생성 → 심의 → (선택) → 승인 게이트를 거친다. 모든 포맷(여러장·한장)이 포맷별 스토리보드·키비주얼을 거치는 것이 의도다(현재 일부 미구현은 글 설명 참조). 00g-guideline(유사사례 "왜 좋은가" 분석)은 동일 도메인 사례가 있을 때만 수행한다.

흐름도를 글로 보기 (화면낭독기·텍스트용)
  1. ⓪ 유형 선언 — 사람이 규제도메인(화장품·의약외품·건기식·의약품)과 산출물 포맷(여러장·한장)을 선언한다. 둘 다 없으면 진행 불가(하드스톱).
  2. 00-ingest — 크롤 번들·워킹백워드·자사 자산을 결정적으로 정규화해 VOC·효능근거표(claim-basis)·자산 매니페스트를 만든다(LLM 없음, 정량의 단일 출처). ⚑ 크롤 사례의 구도·무드 "왜 좋은가" 감각 인사이트 제공이 의도이나, 현재는 정적 사전(BP_HINTS)으로만 — 개선 예정(WS-C).
  3. 분기 — 동일 도메인 유사사례가 있나? 있으면 → 00g-guideline(크롤 유사사례를 분석해 "왜 좋은가" 3안 제안 → 사람 선택), 없으면 곧장 01-brief(기본 레포는 사례 디렉터리 부재 → 자기 번들 폴백). ⚑ 현재 "왜 좋은가"는 정량(할인·평점) 위주 → 시각·감각 인사이트로 확장 예정(WS-C).
  4. 01-brief — PR/FAQ로 정리(효능 단정 대신 VOC 키워드, 미승인 기능성은 카피 배제, 규제·실증 리스크는 내부 FAQ·민감 라벨로).
  5. 02-concept — 컨셉 축별 RTB·키메시지를 다안 생성 → 사람 선택.
  6. 03-storyboard (모든 포맷) — 포맷별(한장·여러장) 스토리라인·아웃라인을 "좋은 키비주얼이 나오도록" 기획·리서치한다. 포맷이 골격을 결정(한장=1매 압축, 여러장=12블록). ✅ M7/M8/G6: 모든 포맷이 03·04를 거친다(format-aware 스토리보드 + 키비주얼 프롬프트 포맷 분기 → 실 LLM 포맷-native; stub 키비주얼은 generic 세로 템플릿).
  7. 04-keyvisual — 확정 기획안을 디자인(여러장=HTML/CSS 2안, 한장=1매)으로 렌더·캡처 후 협회 제출 패키지(kcia-package) export. img src는 자사 자산만.
  8. done — 최종 패키지(포맷별 산출물).
  9. 각 생성 페이즈 공통 게이트 — 생성 → 심의(kcia-check: 결정적 룰엔진 + 다른 세션 critic 2-pass) → [다안이면 사람 선택] → 사람 승인. 심의 fail·보완요청이면 같은 페이즈를 재생성(iteration+1), 반복 상한(00g·brief·concept=3, storyboard=4, keyvisual=2) 초과면 escalated(사람·RA 개입). 비활성 도메인(의약외품·건기식)은 심의 자동 통과(placeholder-autopass).
  10. 심의 순서 — 현재 구현은 생성 → 심의 → 승인. 재설계(GBP 정본) 목표는 생성 → 사람 승인 → 심의로 한 칸 이동(WS-A, 미구현).
