# chat/jobs — 생성 잡 큐 (프로토콜 v2)

챗 레이어는 **온라인에서 실엔진 생성을 스스로 띄우지 않는다**(헤드리스 실엔진 = core fail-closed, C3 금지).
대신 `BridgeGenExecutor` 가 생성 요청을 이 폴더에 **파일로 적재**하고, **소비자**가 그 파일을 집어 세션 내(insession)
생성으로 런을 전이시킨다. 챗 레이어는 next-action 폴링으로 전이를 감지해 재개한다.

소비자는 셋이고, **이 폴더의 규약이 그 셋의 유일한 이음새**다:

| 소비자 | 누구 | 상태 |
|---|---|---|
| 사람 운영자 | 운영자의 Claude Code 세션이 잡을 손으로 소비 | 오늘의 기본 경로 |
| 무인 데몬 | 별도 프로세스가 잡마다 세션을 띄워 소비 | 후속 단계 |
| 봇 | 잡을 **적재**하고 전이를 기다리는 쪽(소비자 아님) | 현행 |

> 오프라인/CI 는 `StubDirectGenExecutor` 가 `run-stage.sh` 를 직접 돌린다(결정적) — 이 폴더를 쓰지 않는다.
> 규약의 코드 SSoT = [`../src/kernel/job-protocol.ts`](../src/kernel/job-protocol.ts). 이 문서와 그 모듈은 같은
> 변경에서 함께 고친다(규약이 두 곳에 있으면 갈라진다).

## 디렉터리

전부 **gitignore**(운영 산출물).

```
jobs/pending/<run_id>-<stage>.json           # 적재된 잡(아직 아무도 안 집음)
jobs/claimed/<소비자>/<run_id>-<stage>.json   # 그 소비자가 집은 잡(작업 중)
jobs/failed/<run_id>-<stage>.json            # 실패·만료 격리
jobs/failed/<run_id>-<stage>.json.reason     #   그 사유(사람이 읽는 한 줄)
```

한 런의 한 단계 = 잡 1건이다(파일명이 `<run_id>-<stage>`). 같은 단계를 다시 요청하면 옛 잡을 **더 신선한 요청으로
대체**한다 — 중복 잡이 쌓이지 않는다(대체하는 방법은 아래 '봇 규약'의 **적재 전 원자 대체**).

## 잡 파일 형식(v2)

```json
{
  "version": 2,
  "kind": "generate",
  "run_id": "chat-slack-C0…-895939",
  "stage": "intake",
  "job_id": "3f2a…",
  "enqueued_at": "2026-07-16T12:04:37.000Z",
  "expires_at": "2026-07-16T12:19:37.000Z"
}
```

| 필드 | 뜻 |
|---|---|
| `kind` | 항상 `generate`. 승인·선택 같은 **결정은 큐를 타지 않는다**(사람이 버튼으로 — 무인화 범위는 생성뿐). |
| `run_id`·`stage` | `run-stage.sh <stage> <run_id>` 인자. |
| `version` | 프로토콜 버전. 없으면 v1 레거시 잡(아래 절 참조). |
| `job_id` | 이 적재 1건의 도장. 봇의 회수가 '자기 잡'만 지우게 한다. |
| `enqueued_at` | 적재 시각(ISO-8601 UTC). |
| `expires_at` | **절대 마감** = `enqueued_at` + `CHAT_BRIDGE_TIMEOUT`(기본 900초). 종단 마감 단일 원천. |

`expires_at` 이 기간이 아니라 **절대시각**인 이유: 늦게 집은 소비자는 잡이 언제 적재됐는지 모른다. 절대시각이라야
"지금 집어도 되나"를 스스로 판단할 수 있다. 봇의 대기 마감도 같은 값에서 나온다(시계가 둘이면 어긋난다).

## 수명주기

```
적재(봇)   pending/X   (expires_at = 적재시각 + CHAT_BRIDGE_TIMEOUT)
   ↓ 소비자가 2중 검사 → 통과하면 클레임(mv pending/X claimed/<나>/X)
작업       claimed/<나>/X 를 들고 세션 안에서 산출물 작성 → run-stage 전이
   ↓
성공       rm claimed/<나>/X          (봇은 next-action 폴링으로 전이를 감지 — 카드가 자동 갱신된다)
실패       mv claimed/<나>/X failed/X + X.reason 기록   (부분 성공 없음)
```

검사에서 걸러진 잡의 처분:

| 판정 | 처분 |
|---|---|
| 만료(남은 시간 < 필요 시간) | `failed/` + `.reason` — 집지 않는다 |
| 이미 전이됨(그 단계 차례가 아님) | 잡 삭제 — 할 일이 이미 끝났다 |
| 마감 미기재(v1 레거시) | 손대지 않는다(사람 소비자 몫) |
| next-action 조회 실패 | 손대지 않는다(판단 불가 — 다음 회차에 다시 본다) |

## 소비자 규약 — 집고 나서 2중 검사

**사람이든 데몬이든 똑같이**, 일을 시작하기 전에 둘 다 확인한다. 하나라도 어긋나면 일하지 않는다.

1. **시간이 되는가** — `지금 + 이 잡에 쓸 시간 + 기동 여유 ≤ expires_at`.
   '마감이 아직 안 지났나'가 아니라 **'끝낼 수 있나'** 를 본다. 마감 1분 전에 10분짜리 생성을 시작하면, 봇은 이미
   포기해 실패 안내를 띄웠는데 결과만 뒤늦게 도착한다(현업이 본 것과 실제가 어긋난다).
2. **아직 그 차례인가** — `bash <core>/scripts/next-action.sh <run_id>` 의 `step` 이 `generate` 이고 `stage` 가
   잡의 stage 와 같아야 한다. `step` 만 보면 안 된다: 그건 페이즈를 가로지르는 전역이라, 다음 단계의 생성 차례를
   옛 잡의 차례로 오인한다.

**★ 순서: 먼저 집고(claim), 집은 것을 검사한다.** 검사부터 하면 **검사한 잡과 집은 잡이 다를 수 있다** — `mv` 는
잡이 아니라 **경로**를 집는데, 그 사이 같은 이름으로 새 잡이 들어올 수 있기 때문이다(같은 단계를 다시 요청하면
봇이 그 이름의 잡을 새 요청으로 대체한다). 그러면 검사 안 한 잡을 들고 일하거나, 멀쩡한 새 잡을 남의 판정으로
`failed/` 에 처박는다.
집은 뒤에 검사하면 검사 대상과 처분 대상이 같음이 보장되고(경합에 진 쪽은 아무것도 만지지 않는다), 느린
next-action 조회 동안 마감이 닳는 문제도 같이 사라진다.

예외 하나 — **v1 레거시(마감 미기재)는 집지도 않는다**: 그건 파일만 열어 보면 알 수 있고(셸 0), 집었다 되돌리면
사람이 손으로 소비 중인 파일을 흔들게 된다(아래 'v1 레거시 잡' 절).

**클레임은 `mv`(rename) 로 한다.** 두 소비자가 같은 잡을 동시에 집으면 rename 은 하나만 성공하고 나머지는
"파일이 없다"로 진다 — 원자성을 OS 가 보장한다. 잠금 파일이나 "있는지 보고 옮기기"로 대신하지 않는다(그건 경합에 열려 있다).

## 사람 소비자 규약(운영자)

운영자가 손으로 소비할 때도 위 규약을 그대로 따른다. 소비자 이름은 자기 토큰 하나를 정해 쓴다
(영숫자·`.`·`_`·`-` 64자 이내, 예 `op-chabh`). `.` 이나 `..` 는 이름이 아니라 경로 이동이라 쓰지 않는다 —
`.` 은 클레임이 `claimed/` 바로 밑에 놓여 reaper 가 못 찾고, `..` 는 잡을 `jobs/` 밖으로 내보낸다(코드도 거부한다).

```bash
cd chat

# 0) 대기줄 훑기 — 어떤 잡이 있는지만 본다(여기서 읽은 내용으로 판정하지 않는다: 아래 2)에서 집은 실물로 다시 본다)
#    ★ 대기줄의 잡은 봇이 **언제든 원자적으로 대체**할 수 있다(위 '적재 = 원자 대체'). 그래서 여기서 cat 으로 본
#      내용은 다음 순간의 사실이 아니다 — 판정은 **내가 실제로 집은 물리 파일**로만 한다(2). 미리 본 내용은 힌트일 뿐.
ls jobs/pending/

#    여기서 가르는 것은 하나뿐 — 마감(expires_at)이 아예 없으면 v1 레거시 잡이니 집지 말고
#    아래 'v1 레거시 잡' 절의 방식으로 소비한다.
grep expires_at jobs/pending/<run_id>-<stage>.json

# 1) 클레임 — **검사보다 먼저**(위 '집고 나서 2중 검사' 절). mv 가 성공해야 내 잡이다
#    (실패 = 누가 먼저 집었다 → 그냥 넘어간다)
mkdir -p jobs/claimed/<내이름>
mv jobs/pending/<run_id>-<stage>.json jobs/claimed/<내이름>/

# 2) 집은 실물을 읽는다 — run_id·stage·expires_at. 아래 두 검사는 전부 이 파일에 대해서 한다
cat jobs/claimed/<내이름>/<run_id>-<stage>.json

# 3) 검사 ①(시간): 지금(UTC)과 expires_at 을 견준다. 남은 시간이 '이 단계에 쓸 시간'보다 짧으면
#    전이하지 않는다 → 아래 '마감이 지났거나 빠듯할 때'로 간다.
date -u +%Y-%m-%dT%H:%M:%SZ

# 4) 검사 ②(차례): step=generate 이고 stage 가 집은 잡의 stage 와 같은지 확인
bash "$HARNESS_ROOT/scripts/next-action.sh" <run_id>
#    이미 전이됐으면(그 차례가 아님) 할 일이 이미 끝난 것 → 잡을 지우고 끝낸다(재실행 금지)
#    rm jobs/claimed/<내이름>/<run_id>-<stage>.json

# 5) 작업 — 둘 다 통과했을 때만. Claude Code 세션 안에서 그 단계 산출물을 **먼저 작성**한다
#    (슬래시 `/<stage>` 스킬 또는 직접 작성)

# 6) 전이 — 검증·전이는 스크립트가 한다(산출물이 없으면 스크립트가 친절히 중단한다)
HARNESS_CLI=claude HARNESS_GEN_MODE=insession bash "$HARNESS_ROOT/scripts/run-stage.sh" <stage> <run_id>

# 7) 마무리
rm jobs/claimed/<내이름>/<run_id>-<stage>.json                     # 성공 → 잡 삭제(전이는 봇이 폴링으로 감지)

# 또는 실패·포기 (failed/ 는 gitignore 라 새 체크아웃엔 없다 — 먼저 만든다)
mkdir -p jobs/failed
mv jobs/claimed/<내이름>/<run_id>-<stage>.json jobs/failed/
echo "사유 한 줄" > jobs/failed/<run_id>-<stage>.json.reason
```

**마감(`expires_at`)이 지났거나 빠듯하면 전이하지 않는다.** 잡을 `failed/` 로 옮기고 사유에 "만료"를 적는다
(`mkdir -p jobs/failed` 먼저 — 위와 같다).
현업은 이미 실패 안내를 받은 뒤라, 늦은 전이는 "스레드엔 실패라고 떴는데 런은 넘어가 있는" 어긋남을 만든다.
꼭 이어서 해야 하면 **스레드에서 그 단계를 다시 요청**하게 해 새 잡(새 마감)을 받는다 — 현업이 실패 카드의
[상태 다시 확인] → [다시 만들기] 를 누르면 된다(아래 봇 규약).

**이 보증은 절차적이다.** 데몬은 잡의 종료 시각을 마감에 묶어 구조적으로 못 넘기게 하지만, 사람에게 타이머를
강제할 수는 없다 — 그래서 위 규약이 곧 보증이다. 어긋났을 때의 안전망은 현업이 실패 카드의
**[상태 다시 확인]** 을 눌러 지금 상태를 다시 받는 것이고, 그 아래 최종 방어는 core 의 락·멱등 게이트다.

## 봇 규약(BridgeGenExecutor)

- **적재 = 원자 대체(supersede-then-create)**: 봇은 새 잡을 **세 걸음으로만** 낳는다. 이 셋은 갈라놓을 수 없다 —
  '검사하고 나서 적재'가 아니라 **적재가 곧 검사**다.

  1. **옛 잡을 내린다** — `rm pending/X`(없으면 그만 = 정상). 이 순간부터 그 옛 잡을 집을 수 있는 자는 없다.
  2. **산 클레임을 본다** — `claimed/*/X` 에 마감이 남은 클레임이 있으면 **적재하지 않는다**
     (현업에겐 "이미 만들고 있어요 — 잠시 후 다시 확인해 주세요").
  3. **배타 생성** — `expires_at`(= 적재시각 + `CHAT_BRIDGE_TIMEOUT`)과 `job_id` 를 실어, 목적지가 비어 있을 때만
     잡는다(이미 있으면 1.로 **한 번만** 되돌아간다. 두 번째도 막히면 "지금 상태를 확인하지 못했어요").

  **왜 1.이 먼저인가(이게 요점이다)**: 클레임은 오직 `pending/X` 에서만 태어난다(`mv pending/X claimed/<나>/X` 말고
  잡이 `claimed/` 로 갈 길이 없다). 그러니 그 파일을 **먼저** 없애면, 어떤 클레임이든 둘 중 하나로 갈린다 —
  ㉮ 우리가 지우기 **전에 이미 성공했다** → 그 클레임은 2.에서 `claimed/` 에 보인다 → 막는다.
  ㉯ 지운 **뒤에 시도한다** → 집을 물건이 없어 진다(`mv` 가 ENOENT). `rm` 과 `mv` 중 정확히 한쪽만 파일을 갖는 것은
  OS 가 보장한다. 즉 "검사는 통과했는데 그 직후 옛 잡이 집히고, 봇은 새 잡을 넣어 **둘이 동시에 도는**" 결말은
  창이 좁아진 게 아니라 **성립하지 않는다**(검사할 무렵 집힐 물건이 이미 없다).

  이 차단이 없으면 [다시 만들기] 가 **새 잡**을 적재해, 옛 잡을 집은 소비자와 새 잡을 집을 소비자가 **같은 런을
  동시에 쓴다**(이중 소비·이중 과금). "[다시 만들기]는 클레임된 잡을 되살리지 않는다"는 보증은 **같은 잡 파일**에만
  참이라 이 결말을 막지 못한다.

  2.의 판정 기준은 **마감뿐**이다(소비자의 생사를 묻지 않는다 — reaper 도 같은 규칙을 쓴다):

  | 클레임 상태 | 새 요청 |
  |---|---|
  | 마감이 남음(`expires_at` > 지금) | **막는다** — 그 소비자는 마감까지 일할 권리가 있다 |
  | 마감 지남 | 막지 않는다 — 규약상 아무도 마감 뒤엔 일하지 않는다(죽은 클레임이 런을 영영 묶으면 안 된다) |
  | 마감 미기재(v1 레거시) | **막는다**(fail-closed) — '죽었다'를 증명할 수 없다(사람이 손으로 소비 중일 수 있다) |
  | 조회 자체가 실패(권한·IO) | **막는다**(fail-closed) — 잘못 막으면 잠시 후 다시 확인하면 되지만, 잘못 적재하면 되돌릴 수 없다 |

  - **정책은 그대로**: 같은 이름의 옛 잡은 **더 신선한 요청으로 대체**한다(같은 일의 옛 요청 · v1→v2 승격 경로 포함).
    바뀐 것은 **방법**뿐이다 — '덮어쓰기'에서 '원자 제거 + 배타 생성'으로.
  - **소비자가 볼 수 있는 것**: 대기줄에 보이던 잡이 예고 없이 사라질 수 있다(봇의 대체). 규약은 그대로다 —
    집기는 `mv` 성공 여부로 갈리고, 대체된 잡은 애초에 집히지 않는다(`mv` 가 ENOENT 로 진다 = 정상 패배).
  - ⚠ **남는 한계(정직하게)**: ㉠ 이 원자성은 **로컬 POSIX 파일시스템** 전제다(`rm`·`mv`·하드링크가 원자적이고
    그 결과가 즉시 보인다). `jobs/` 를 NFS·FUSE 같은 곳에 두면 이 보증이 깨진다. ㉡ **적재자는 봇 하나**라는
    배치 전제도 그대로다(Socket Mode 봇 = 워크스페이스당 1 프로세스). 봇을 다중화하면 3.의 배타 생성이 계속
    막혀(`unknown`) 적재가 서로를 물어뜯는다. ㉢ 그 아래 최종 방어는 여전히 core 의 락·멱등 게이트다.

- **대기**: next-action 폴링으로 전이를 감지하면 남은 pending 잡을 정리하고 완료 처리.
- **타임아웃 = 회수**: 대기 상한을 넘기면 아직 `pending/` 에 있는 **자기 잡**(job_id 대조)을 거둬들인다 — 봇이
  포기한 뒤 소비자가 뒤늦게 집어 '봇 몰래' 되살리는 창을 닫는다. 같은 단계로 새로 적재된 잡(job_id 다름)은 남의
  요청이라 건드리지 않는다.
- **회수 실패 = 늦은 성공 가능**: 이미 클레임된 잡은 회수할 수 없다(봇은 남의 프로세스를 죽이지 못한다). 그때는
  실패 카드의 **[상태 다시 확인]** 버튼이 화해를 맡는다 — 누르면 next-action 을 다시 읽어 지금 게이트 카드를
  그린다(상태를 바꾸지 않는 읽기 전용이라 어떤 게이트도 우회하지 않는다). 그 뒤 [다시 만들기] 를 눌러도 위
  **적재 2단계(산 클레임 조회)** 가 막는다(그 소비자의 마감이 남아 있는 한) — 화해는 기다림이지 두 번 만들기가 아니다.
- **회수 성공 = 요청이 사라짐 → [다시 만들기]**: 아무도 안 집은 채 봇이 포기하면 그 요청은 큐에서 없어지는데,
  core 는 그대로 그 단계 생성 차례에 서 있다. 그래서 [상태 다시 확인] 이 next-action 을 다시 읽어 **여전히 생성
  차례**임을 확인하면, 봇은 "만드는 중"이라 둘러대지 않고 **[다시 만들기]** 버튼을 낸다. 그 클릭은 옛 잡을
  되살리는 게 아니라 **새 요청(새 `job_id`·새 `expires_at`)** 을 적재한다 — 누르는 순간 다시 한 번 next-action 을
  확인하므로, 그새 소비자가 늦게 성공했으면 요청 대신 지금 게이트 카드가 뜬다(끝난 일을 다시 시키지 않는다).

## 남은 클레임 뒷정리(reaper) — 마감이 곧 리스

소비자가 잡을 집은 채 끝내지 못하면 `claimed/<소비자>/` 에 잡이 남는다. reaper 는 그것을 **마감(리스)만 보고**
처분한다 — 소비자가 살아 있는지 **묻지 않는다**:

| 클레임 상태 | 처분 |
|---|---|
| **마감이 남음** | **불가침** — 손대지 않는다. 그 소비자는 마감까지 일할 권리가 있다(적재 차단과 같은 규칙) |
| 마감 지남 + 이미 전이됨 | 잡 삭제 — 다 끝난 일의 흔적만 치운다 |
| 마감 지남 + 아직 그 단계 생성 차례 | `failed/` + `.reason`("만료") — **대기줄로 되돌리지 않는다** |
| 마감 미기재(v1 레거시) | 손대지 않는다 — 생사를 알 수 없는 것에 손대지 않는다(사람 몫) |
| 잡 파일이 깨짐 | `failed/` + `.reason` — 마감을 못 읽으면 리스를 존중할 근거도 없다 |
| next-action 조회 실패 | 손대지 않는다(판단 불가 — 다음 회차에 다시 본다) |

**왜 '살아 있나'를 묻지 않는가**: 하트비트가 멈춘 것은 죽음이 아니다(멈췄다 재개하는 소비자·느린 소비자·
하트비트만 끊긴 소비자). 그 추정이 한 번만 틀려도 원래 소비자와 되살아난 잡을 집은 새 소비자가 **같은 런을 동시에
쓴다** — 이중 소비를 막아야 할 reaper 가 그 원천이 된다. 그래서 근거를 추측(하트비트)에서 **파일에 박힌 사실
(`expires_at`)** 로 바꿨다.

**왜 되돌리지 않는가(재큐 없음)**: 되돌린 잡에는 새 마감이 필요한데, 마감을 발행하는 자는 봇뿐이다(마감 단일 원천).
reaper 가 마감을 지어내면 그 잡의 마감과 봇의 대기 마감이 갈라진다. 게다가 **정규 복구 경로가 이미 있다** — 만료된
클레임은 새 적재를 막지 않으므로(위 표), 봇의 자동 이어가기나 현업의 [다시 만들기] 가 **새 마감을 단 새 잡**을
적재한다. reaper 가 할 일은 큐가 거짓말하지 않게 흔적을 치우는 것뿐이다.

소비자는 **기동 시 reaper 를 먼저 돌린 뒤 폴링을 시작한다** — 지난 생의 잡을 남겨 둔 채 새로 집으면 같은 이름의
클레임을 자기가 덮어써 그 기록을 잃는다. 사람 운영자도 같다: 자기 `claimed/<내이름>/` 에 남은 잡이 있으면 새 잡을
집기 전에 그것부터 정리한다(끝냈으면 삭제, 마감이 지났으면 `failed/` 로).

## v1 레거시 잡(마감 없는 잡)

프로토콜 v1 은 `{run_id, stage, kind}` 만 썼다 — `expires_at` 이 없다. 그런 잡은 시간 검사를 할 수 없으므로
**자동 소비 대상이 아니다**(마감이 없으면 데몬의 구조적 보증이 성립하지 않는다). 처분:

- 무인 데몬: 집지 않고 **그대로 둔다**(`failed/` 로 강등하지도 않는다 — 남의 대기줄을 함부로 치우지 않는다).
- 사람 소비자: v1 잡은 애초에 **운영자 세션 소비**를 전제로 적재된 것이라, 위 사람 규약대로 소비하면 된다.
  시간 검사 대신 **검사 ②(차례)** 를 반드시 확인한다 — 그게 그 잡이 아직 유효한지의 유일한 근거다.
- 데몬에 넘기려면: 스레드에서 그 단계를 다시 요청해 **새 잡(v2)** 을 받는 것이 정석이다. 부득이하면 운영자가
  `expires_at`(ISO-8601 UTC)과 `job_id` 를 채워 다시 저장한다 — 마감을 새로 거는 것은 사람의 결정이다.

## 완료 판정

브리지는 `next-action.sh <run_id>` 의 `step` 이 `generate` 를 벗어나거나 `stage` 가 바뀌면(사람/심의 게이트 도달)
생성 완료로 본다. `CHAT_BRIDGE_TIMEOUT`(기본 900초) 안에 전이가 없으면 대기 시간 초과로 실패 처리한다(무한 대기 금지).

## P4 / S-1 — 생성 무인화 스파이크 (세션 워커)

**질문:** 운영자 세션(C2 브리지)을 무인 세션 워커로 대체해 브리프 너머까지 **무인** 완주할 수 있는가?

**설계(코드에 반영됨):** `kernel/gen-executor.ts` 의 세 번째 구현 `AgentSdkGenExecutor` 가 그 자리다.
- 실제 생성은 주입된 `sdkGenerate(rid, stage)` 가 한다 — 세션 안에서 산출물을 쓰고
  `HARNESS_CLI=claude HARNESS_GEN_MODE=insession run-stage.sh <stage> <rid>` 로 전이시킨다(운영자가 하던 일을 대신).
- 이 클래스는 그 뒤 `next-action` 으로 전이를 확인한다(브리지와 **동일한 완료 계약**: 요청 stage 가 더 이상 현재 생성
  대상이 아니면 완료). 확인 안 되면 fail-closed.

**선택 규칙:** `selectGenExecutor()` — 오프라인=StubDirect · 온라인=**Bridge(C2, 검증된 기본)** · 온라인+`CHAT_GEN_UNMANNED_S1=1`
+`sdkGenerate` 배선 **둘 다** 있을 때만 AgentSdk 로 승격. 하나라도 없으면 브리지로 폴백(S-1 실패/미배선이 다른 단계를
막지 않음 — 계획 P4). 이 레포엔 `sdkGenerate` 가 배선돼 있지 않아 온라인은 항상 브리지(동작 불변).

**검증 상태(스파이크 경계):** 세션 워커 배선·insession 세션 마커(신뢰 감지)는 이 레포에 없어 **오프라인 검증 불가(live-only)**.
- 검증된 것(오프라인 단위 테스트): `selectGenExecutor` 분기(오프→Stub, 온라인 무-S1→Bridge, S-1+SDK→AgentSdk, S-1-무SDK→Bridge),
  `AgentSdkGenExecutor` 의 계약(미배선 fail-closed · 성공+전이확인 · 전이미확인 실패 · 중복 즉시반환),
  프로토콜 v2 수명주기(만료 미클레임 · 전이완료 삭제 · 경합 rename 승자 1명 · **적재 원자 대체** ·
  **reaper 마감 리스**(불가침·재큐 없음) · 봇 타임아웃 회수).
- 미검증(라이브 필요): 실제 세션 워커가 insession 산출물을 쓰고 전이시키는 것, 세션 신뢰 마커 감지.
- **결론:** 무인 소비자가 붙을 자리(프로토콜 v2)는 준비됐고 C2 브리지가 검증된 폴백으로 남아 있다. 무인화 활성화 =
  소비자 구현 배선 + `CHAT_GEN_UNMANNED_S1=1` (core 무수정). 라이브 검증은 후속.
