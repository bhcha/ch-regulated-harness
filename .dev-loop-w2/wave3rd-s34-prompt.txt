적대적 코드 리뷰(재설계 S3+S4 — supervisor 재배선 + 러너 정렬). 추정이 아니라 코드로 논증하라. 없는 결함을 만들지 마라.

이것은 raw-PID heartbeat → nonce ledger 재설계의 **핵심 배선**이다. 불변식 12 = `.dev-loop-w2/review-brief.md`.
diff = `.dev-loop-w2/wave3rd-s34.diff`. 코드는 레포에서 직접 확인(ownership.ts 계약도 함께).

## 배경
5라운드 리뷰가 raw-PID heartbeat 를 '근본 재설계 필요'로 판정 → nonce 원장(ownership.ts, S12-R2 게이트 통과)으로 교체.
S3 = supervisor 가 ownership 소비하도록 재배선(heartbeat 제거·intent-before-spawn·처분 settle). S4 = 러너 정렬(outcome
개명·완전 매핑·now() 가드).

## S3 적용
- heartbeat(createHeartbeatWriter·HeartbeatIo·CHAT_SUPERVISOR_HEARTBEAT) **제거** → createLedger 배선.
- **1차 강제(kill_at 3단·cap-kill·armNext·pgid≤1 방어·종료전파)는 무수정 유지**(리뷰 통과분).
- **intent-before-spawn**: hasSpawnRoom → ledger.intent(nonce, durable) → spawnSession(plan, nonce) → pgid>1 → register.
  intent throw=spawn 안 함·ledger_unwritable · register throw=SIGKILL+실패.
- **처분 settle(high#1 흡수)**: 소멸확인 outcome→reaped+release · reap_failed(그룹 생존)→leaked(디스크·인메모리 잔존,
  release 안 함).
- 옛 과대주장 주석(kill(-pgid,0)+supervisorPid 로 PID재사용 닫음) 제거.
- supervisor 테스트를 supervisor.test.ts 로 분리.

## S4 적용
- outcome 개명 heartbeat_unwritable→ledger_unwritable(전량, grep 0 확인). role 스레딩(recovery 라벨).
- defaultSupervise **드롭**(ledger 없이 runtime throw 하던 dead path) → supervise 를 required dep 로.
- **완전 매핑**: classifyOutcome 이 모든 SessionOutcome→RunJobResult(never 가드). exited/killed 만 전이확인,
  성공(ok:true)은 실제 전이 시만. 나머지는 전이확인 전 타입드 실패.
- now() try/catch 밖 → config_error 로 가드.
- ⚠ S4 가 supervisor.ts 를 2곳 편집(union 멤버 삭제·main() 클로저 role 전달) — 로직 0 변경이라 주장.

## 판정 요청
⑴ **intent-before-spawn 이 register-lag 을 실제로 닫는가**: 순서가 코드에서 강제되는가(happens-before)? intent durable
   반환 전에 spawn 이 절대 안 불리는가? intent 실패 시 spawn 0·회수 0 이 성립하는가? register 실패 시 SIGKILL+실패가
   fail-closed 인가?
⑵ **처분 settle 이 high#1 을 실제로 흡수하는가**: reap_failed 가 **모든** 경로에서 leaked(잔존)인가, reaped(삭제)로
   새는 경로가 하나라도 있는가? 인메모리 그룹이 leaked 시 종료전파 대상으로 남는가? register 실패 경로의 best-effort
   settle(reaped)이 살아있는 그룹을 조기 삭제하지 않는가?
⑶ **outcome 매핑이 완전하고 안전한가(★ 이 재설계의 핵심 버그류)**: classifyOutcome 이 **모든** SessionOutcome 을
   처리하는가? 미매핑 outcome 이 **성공으로 falls-through** 하는 경로가 하나라도 있는가(never 가드가 컴파일+런타임
   양쪽을 막는가)? exited/killed+미전이+산출물없음이 실패인가? recovery 경로도 동일 안전한가?
⑷ **1차 강제 무수정 확인**: kill_at·cap-kill·armNext·pgid 방어·종료전파가 S3 에서 **실제로 무변경**인가, 아니면
   재배선하며 미묘하게 깨진 곳이 있는가(특히 종료전파가 이제 ledger 아닌 인메모리 레지스트리를 도는데 leaked 잔존과의
   상호작용)?
⑸ **S4 의 supervisor.ts 편집**이 로직 0 변경 주장대로인가, 아니면 실제 동작을 바꿨는가? role 전달이 evaluateReap 에
   영향 주는가(라벨 전용이라 무영향이 맞는가)?
⑹ start-time 기록(Date.now()-process.uptime()*1000)이 supervisor 실제 시작시각인가? 그 외 새 결함.
